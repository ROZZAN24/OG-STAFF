📐 1. What is the RSA Algorithm?

RSA (named after Ron Rivest, Adi Shamir, and Leonard Adleman who publicly described it in 1977) is an asymmetric public-key cryptosystem based on the mathematical difficulty of factoring the product of two large prime numbers.

In textbook RSA:

  • Two large, distinct prime numbers $p$ and $q$ are chosen at random.
  • The modulus $n$ is calculated as $n = p \times q$. The bit-length of $n$ defines the key length (e.g. 2048 bits in this project).
  • Euler's totient function is computed: $\phi(n) = (p - 1)(q - 1)$.
  • A public exponent $e$ is chosen such that $1 < e < \phi(n)$ and $\gcd(e, \phi(n)) = 1$. The standard industry standard value is $e = 65537$ ($2^{16} + 1$).
  • The private exponent $d$ is computed as the modular multiplicative inverse of $e \pmod{\phi(n)}$, satisfying: $e \cdot d \equiv 1 \pmod{\phi(n)}$.

Implementation Note: Modern cryptographic libraries like the W3C Web Crypto API (`window.crypto.subtle`) generate cryptographically secure primes in constant-time internal routines. This application delegates key generation directly to the browser's hardware/OS crypto engine rather than manually picking primes in JavaScript.

⚖ 2. Digital Signatures vs Encryption

While both operations utilize asymmetric key pairs, their design objectives and key usage are polar opposites:

Dimension Digital Signature (RSASSA-PKCS1-v1_5) Asymmetric Encryption (RSA-OAEP)
Primary Goal Authenticity, Integrity, Non-Repudiation Confidentiality & Secrecy
Sender Action Signs using sender's Private Key Encrypts using recipient's Public Key
Receiver Action Verifies using sender's Public Key Decrypts using recipient's Private Key
Plaintext Visibility Data remains fully visible and readable Data is scrambled into ciphertext
ID Card Context Security guards must read the name, but verify authenticity Encrypting the card would prevent guards from reading it

In OG STAFF, the staff card fields (Name, ID, Department) remain readable plaintext, accompanied by a 256-byte digital signature verifying that the institution authored the record.

⚡ 3. SHA-256 Cryptographic Hash Function

RSA signing cannot be applied directly to arbitrary-length documents because RSA arithmetic is computationally expensive and limited to messages smaller than the modulus $n$. Therefore, a cryptographic hash function like SHA-256 (Secure Hash Algorithm 256-bit) is used:

  • Fixed Digest Length: Maps arbitrarily large data to a deterministic 32-byte (256-bit) digest.
  • Preimage Resistance (One-Way): Given a hash $H$, it is computationally infeasible to find $M$ such that $\text{SHA-256}(M) = H$.
  • Collision Resistance: Computationally impossible to find two distinct messages $M_1 \neq M_2$ yielding $\text{SHA-256}(M_1) = \text{SHA-256}(M_2)$.
  • Avalanche Effect: Changing even a single bit in the input alters approximately 50% of the output bits in a pseudo-random fashion.

Crucial Viva Point: A SHA-256 hash alone is not a digital signature. Anyone can recompute the SHA-256 hash of modified data. A signature requires encrypting the hash using the private key, binding the content to the signer's identity.

🌐 4. The W3C Web Crypto API

The project uses exclusively the native W3C Web Crypto API (`window.crypto.subtle`):

  • crypto.subtle.generateKey(): Generates the 2048-bit RSA key pair with RSASSA-PKCS1-v1_5 and SHA-256.
  • crypto.subtle.sign(): Signs the UTF-8 canonical byte array using the institutional private key.
  • crypto.subtle.verify(): Verifies the 256-byte signature against the canonical byte array using the trusted public key.
  • crypto.subtle.digest(): Computes raw SHA-256 digests for public key fingerprints and educational audit logging.
  • crypto.subtle.exportKey() / importKey(): Serializes and deserializes keys in standard JWK and SPKI formats.

Secure Context Requirement: Web Crypto APIs are restricted by browser security policies to Secure Contexts (HTTPS or `http://localhost`). Serving via `http://localhost:8080` fulfills this requirement.

📊 5. Barcode Technology: Code 128 vs QR Codes

In this project, QR codes have been completely replaced with traditional 1D Code 128 barcodes.

Code 128 Characteristics:

  • High-density 1D linear barcode supporting the complete ASCII 128 character set.
  • Contains start/stop characters and a modulo-103 checksum character for scan error detection.

Practical Density Limitation & The Compact Token Strategy:

A 2048-bit RSA signature encoded in Base64 is 344 characters long. Adding JSON staff fields produces a payload exceeding 500 characters. In a 1D barcode, encoding 500 characters results in an impractically wide barcode that cannot fit on a standard 85.6mm × 54mm ID badge and cannot be read by consumer cameras.

Therefore, this project employs an institutional reference strategy:

  1. The Code 128 barcode encodes a compact, printable token (e.g. OG-STF-XXXX).
  2. The complete signed record is stored in the verifier's database / LocalStorage under that token, or imported via a signed JSON file.
  3. Scanning the barcode retrieves the full signed record, and the verifier mathematically verifies the RSA signature using the trusted public key.

Remember: Decoding a barcode merely extracts characters. It provides zero security. Cryptographic authenticity comes entirely from the RSA signature verification.

⚙ 6. Step-by-Step Verification Algorithm

  1. Receive Input: Verifier acquires the staff record and Base64 digital signature via barcode lookup, JSON file, or manual entry.
  2. Schema Validation: Confirm required canonical fields (`staffId`, `staffName`, `department`, `designation`, `institution`, `joiningDate`, `validUntil`) are present.
  3. Select Trusted Public Key: Obtain the institution's public key from a trusted local store or certificate. Never trust a key inside the barcode!
  4. Canonicalize Data: Construct the canonical JSON object with exact key ordering and serialize to UTF-8 bytes using TextEncoder.
  5. Decode Signature: Convert the 344-character Base64 signature into a 256-byte ArrayBuffer.
  6. Execute Cryptographic Verification: Invoke crypto.subtle.verify(). If the signature does not match, return INVALID immediately.
  7. Evaluate Expiration: Independently compare the ISO date validUntil against current local date. If expired, return EXPIRED (authentic, but lapsed).
  8. Conclude: If signature is valid and date is unexpired, return VERIFIED.

🛡 7. Tampering Detection & Unsigned Fields

Because RSASSA-PKCS1-v1_5 binds the private key to the exact SHA-256 digest of the canonical string, any unauthorized change — such as changing "Assistant Professor" to "Professor" — alters the canonical string, alters the SHA-256 hash, and causes crypto.subtle.verify() to fail.

Unsigned Fields (E.g. Photo): In this project, the staff photograph is for visual display only and is deliberately excluded from the canonical signature payload to keep payloads compact. Consequently, replacing the photograph would not trigger a cryptographic signature failure. In a production government ID system, a SHA-256 hash of the photo bytes would also be included inside the canonical payload.

⚠️ 8. Security Limitations (Educational Prototype vs Production)

When discussing this project during a viva examination, students must demonstrate security awareness by identifying the prototype's real-world limitations:

  • Private Key in LocalStorage: LocalStorage is accessible to any script running on the origin and anyone with physical access to the browser profile. Production systems must store private keys in Hardware Security Modules (HSMs) or cloud KMS.
  • Public Key Trust & Distribution: The prototype relies on manual public key loading. Production requires a Public Key Infrastructure (PKI) with hierarchical Certificate Authorities (CAs).
  • Revocation: The system lacks an online Certificate Revocation List (CRL) or OCSP responder to revoke keys or badges before their expiration date.
  • Barcode Cloning: Anyone can photocopy a 1D barcode. Without biometric confirmation or a secure challenge-response chip (like an NFC smart card), barcodes can be cloned.

🎓 9. Top 10 Security Laboratory Viva Questions & Answers

Q1. What is RSA, and why is it called an asymmetric cryptosystem?
RSA is a public-key cryptosystem based on modular arithmetic and the integer factorization problem. It is called asymmetric because it uses two mathematically linked but distinct keys: a public key for encryption or signature verification, and a private key for decryption or signing. Knowledge of the public key does not reveal the private key.
Q2. What is the fundamental difference between public and private keys in digital signatures?
In digital signing, the private key must remain confidential to the signing authority (e.g. the college registrar) and is used to create digital signatures. The public key is published to all verifiers (e.g. security guards, campus gates) and is used solely to verify that the signature was created by the matching private key.
Q3. What security properties does a digital signature provide?
A digital signature provides three core security services: Authenticity (proves the true identity of the signer), Data Integrity (proves the document was not altered in transit), and Non-repudiation (the signer cannot deny having signed the document).
Q4. Why is SHA-256 hashing performed prior to RSA signing?
Direct RSA calculation is computationally expensive and limited to inputs smaller than the key modulus (e.g., 2048 bits / 256 bytes). Hashing compresses an arbitrary-length document into a fixed 256-bit digest in constant time, allowing RSA to sign only the digest while preserving collision resistance.
Q5. Why does this project strictly enforce canonical JSON before signing?
JSON objects in JavaScript have indeterminate key serialization orders, and different parsers may format spacing or newlines differently. Canonicalization guarantees that the exact same key order and byte sequence is evaluated during both signing and verification. If even a single space or key position changed, the SHA-256 hash would differ, causing verification to fail.
Q6. What is the Avalanche Effect, and how does it detect tampering?
The avalanche effect is a property of cryptographic hash functions where changing even a single bit of input flips approximately 50% of the output bits pseudo-randomly. When an attacker alters one character in a staff ID, the computed SHA-256 hash changes completely, making it impossible for the original signature to match.
Q7. Why is a barcode not a security mechanism by itself?
A barcode is merely an optical representation of alphanumeric characters. Anyone can print or copy a barcode using free online generators. Security comes exclusively from the cryptographic digital signature verified after decoding the barcode.
Q8. Why must the public key be obtained from a trusted out-of-band source rather than the barcode?
If the verifier trusted a public key embedded in the barcode itself, an attacker could generate their own key pair, sign forged staff data with their own private key, and provide their own public key. The verification math would succeed! True security requires verifying against the institution's pre-configured, trusted public key.
Q9. How does this system distinguish between an EXPIRED record and an INVALID record?
Signature verification and expiration are independent checks. If the signature is mathematically valid but the calendar date has passed validUntil, the badge is marked EXPIRED (genuine, but no longer active). If the signature does not match, it is marked INVALID (forged or tampered). An expired badge that has also been tampered with is always classified as INVALID.
Q10. What are the risks of storing RSA private keys in browser LocalStorage?
LocalStorage offers no encryption at rest, is accessible to any JavaScript running on the origin (vulnerable to Cross-Site Scripting / XSS), and can be inspected by anyone with access to the computer's user profile. In production, private keys must be protected in Hardware Security Modules (HSMs) or cloud Key Management Services (KMS).
